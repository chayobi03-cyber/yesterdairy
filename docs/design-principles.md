# 설계 원칙 (진행하며 얻은 교훈)

- **비용 추가 금지**: 유료 API·외부 이미지 라이선싱·생성형 이미지 등 운영비가
  드는 요소는 기본적으로 배제. 세계관 비주얼(나무/별자리/행성/색모음집)은
  전부 CSS/SVG로만 그리고, 새 아이템·세계관을 추가할 때도 이 기준을 먼저 통과
  시킬 것.
- **랜덤 없음, 결정론적 해금만**: 어떤 보상이든 "무엇을 줄지"는 고정 ID(아이템
  id, 유저 id 등)를 해시한 값으로 정한다 (`h = (h*31+charCode)>>>0; h % n`
  패턴, `lib/colors.ts`/`lib/creatures.ts`/캘린더 작성자 점 색 등에서 재사용).
  `Math.random()`으로 보상을 결정하지 않는다.
- **RLS로 필터링을 대신한다**: 캘린더·가족 피드·앨범처럼 "내 것 + 가족이 공개한
  것"을 보여줘야 하는 쿼리는 `.eq("user_id", ...)` 필터를 걸지 않고 RLS가
  알아서 좁혀주게 둔다. 단, 새 쿼리를 이렇게 짤 때마다 관련 RLS 정책이 실제로
  존재하는지 먼저 확인할 것 — 존재하지 않으면 조용히 빈 결과만 나온다.
- **Storage RLS는 테이블 RLS와 별개**: `media` 테이블에 family-read 정책이
  있어도 `storage.objects`에 같은 정책이 없으면 실제 파일(서명 URL 발급 포함)은
  가족에게 여전히 안 보인다. 파일이 관련된 기능을 추가할 때는 테이블 RLS와
  스토리지 RLS를 항상 짝으로 점검한다 (마이그레이션 0010 참고).
- **비정규화된 필드는 수동 동기화**: `media.visibility`는 `diary_entries
  .visibility`의 별도 사본이라, 기록 공개범위를 바꿀 때 같이 갱신하지 않으면
  프라이버시 유출로 이어진다. 비슷하게 비정규화된 값이 생기면 갱신 지점을
  전부 찾아 동기화할 것.
- **E2E 테스트 타임아웃은 시나리오 길이에 맞춰 키운다**: 핵심 플로우 테스트가
  스텝을 계속 늘려가는 구조라, 실패가 "매번 다른 스텝에서 타임아웃"으로
  나타나면 코드 버그가 아니라 `playwright.config.ts`의 `timeout`이 이제
  안 맞는 것일 가능성이 높다 — 재시도 전에 먼저 이 가능성부터 확인.
- **하단 탭바는 5개 유지**: 화면을 추가할 때 하단 탭에 무조건 넣지 말고, 이미
  홈 화면 버튼/링크로 한 번에 갈 수 있는 기능(기록 작성, 도전 모드 등)은
  탭 대신 홈 화면 링크로 둔다. 탭바에 새 항목을 넣어야 한다면 기존 항목 중
  중복되는 것을 먼저 빼는 걸 검토할 것.
- **탭 가능해 보이면 실제로 탭 가능해야 한다**: 달력 날짜 칸이 몇 커밋 동안
  그냥 `<div>`였던 것처럼, "이 카드/셀/날짜를 누르면 뭔가 일어날 것 같다"는
  화면을 만들 때 실제 클릭 핸들러/링크를 빼먹기 쉽다. 이런 종류의 버그는
  린트/타입체커로 못 잡는다 — 새 화면·리스트 아이템·그리드 셀을 추가할 때는
  "눌렀을 때 무슨 일이 일어나야 하는가"를 `docs/qa-scenarios.md`에 먼저 한 줄
  적고, 그 줄에 대응하는 E2E 스텝을 실제로 추가하기 전까지는 그 기능을
  완료로 치지 않는다.
- **E2E 스텝은 끝나는 URL을 선언한다**: `tests/e2e/core-flow.spec.ts`의 `step()`
  헬퍼는 각 스텝이 끝났을 때 어느 페이지에 있어야 하는지를 필수로 받는다.
  한 스텝이 페이지를 다른 곳으로 옮겨놓고 돌아오는 걸 잊으면, 그 실수를 한
  스텝 안에서 바로 잡아낸다 — 다음 스텝이 "요소를 못 찾음" 타임아웃으로
  실패해서 원인을 헷갈리게 만드는 대신. 새 스텝을 추가할 때도 이 패턴을
  따를 것.
- **"오늘"은 서버 시각이 아니라 뷰어의 로컬 시각이다**: 서버(Vercel)는 UTC로
  돈다. `new Date()`를 서버 컴포넌트/서버 액션에서 그대로 써서 "오늘 날짜"를
  구하면, UTC보다 앞선 시간대(한국 등)에서 자정 직후에 쓴 기록이 전날로
  기록되는 실제 버그가 난다. "오늘이 며칠인지"가 필요하면 항상
  `lib/today.ts`의 `getTodayISO()`를 쓸 것 — 루트 레이아웃의
  `<LocalDateSync/>`가 뷰어의 브라우저 시계로 `local_date` 쿠키를 계속
  맞춰두고, 서버는 그 쿠키를 읽는다. 새로 "오늘"이 필요한 화면을 만들 때
  `new Date().toLocaleDateString(...)`을 서버 쪽에 직접 쓰지 말 것.
- **"앱이 느리다"는 먼저 실제 근거로 확인한다**: 추측으로 코드부터 고치지
  말고 `mcp__Supabase__get_advisors`(performance/security)와
  `mcp__Supabase__query_logs`부터 본다. 이번에 확인해보니 (1) `diary_entries`
  /`events`/`goals`/`media`에 "owner full access"(FOR ALL) + "family can
  read shared"(FOR SELECT) 두 개의 permissive 정책이 걸려 있어서 SELECT마다
  정책이 두 번 평가되고 있었고 (마이그레이션 0011에서 SELECT 하나로 통합),
  (2) 실사용자는 2명뿐인데 E2E 테스트가 운영 Supabase 프로젝트를 그대로
  씀 — 개발/테스트를 많이 한 날은 `e2e_` 계정 가입·로그인이 auth 로그를
  크게 늘려서 체감 속도에 영향을 줄 수 있다. RLS 정책을 고칠 때는 항상
  owner/family 권한 범위가 그대로인지 기존 E2E(특히 프라이버시 경계,
  storage RLS 테스트)로 재검증할 것.
- **"랜덤처럼 보이지만 실제로는 랜덤이 아닌" 것도 원칙을 지킨다**: "오늘의
  미션 색"은 레퍼런스 앱에서 "랜덤"이라고 부르지만, `lib/color-names.ts`의
  `todayMission()`은 날짜를 해시해서 고른다 — 매일 다르게 느껴지지만 같은
  날엔 가족 모두에게 같은 미션이 뜨고, 재현 가능하다. 겉보기엔 랜덤인
  레퍼런스 기능을 그대로 베낄 때도 "결정론적 해금만" 원칙에 맞게 변형할 것.
- **getUserMedia(카메라)는 CI에서 fake 디바이스로 테스트한다**:
  `playwright.config.ts`의 chromium 프로젝트에 `--use-fake-ui-for-media-stream`
  `--use-fake-device-for-media-stream` 두 플래그를 켜두면 카메라 권한
  프롬프트를 자동 수락하고 합성 영상을 흘려보내줘서, 실제 카메라 없는
  CI 러너에서도 getUserMedia 플로우를 헤드리스로 검증할 수 있다.
