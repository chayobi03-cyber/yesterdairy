# 설계 원칙 (진행하며 얻은 교훈)

- **비용 추가 금지**: 유료 API·외부 이미지 라이선싱·생성형 이미지 등 운영비가
  드는 요소는 기본적으로 배제. 세계관 비주얼(나무/별자리/행성/색모음집)은
  전부 CSS/SVG로만 그리고, 새 아이템·세계관을 추가할 때도 이 기준을 먼저 통과
  시킬 것.
- **랜덤 없음, 결정론적 해금만**: 어떤 보상이든 "무엇을 줄지"는 고정 ID(아이템
  id, 유저 id 등)를 해시한 값으로 정한다 (`h = (h*31+charCode)>>>0; h % n`
  패턴, `lib/colors.ts`/`lib/creatures.ts`/캘린더 작성자 점 색 등에서 재사용).
  `Math.random()`으로 보상을 결정하지 않는다.
- **RLS로 필터링을 대신한다**: 캘린더·가족 피드·앨범처럼 "내 것 + 가족이 공개한
  것"을 보여줘야 하는 쿼리는 `.eq("user_id", ...)` 필터를 걸지 않고 RLS가
  알아서 좁혀주게 둔다. 단, 새 쿼리를 이렇게 짤 때마다 관련 RLS 정책이 실제로
  존재하는지 먼저 확인할 것 — 존재하지 않으면 조용히 빈 결과만 나온다.
- **Storage RLS는 테이블 RLS와 별개**: `media` 테이블에 family-read 정책이
  있어도 `storage.objects`에 같은 정책이 없으면 실제 파일(서명 URL 발급 포함)은
  가족에게 여전히 안 보인다. 파일이 관련된 기능을 추가할 때는 테이블 RLS와
  스토리지 RLS를 항상 짝으로 점검한다 (마이그레이션 0010 참고).
- **비정규화된 필드는 수동 동기화**: `media.visibility`는 `diary_entries
  .visibility`의 별도 사본이라, 기록 공개범위를 바꿀 때 같이 갱신하지 않으면
  프라이버시 유출로 이어진다. 비슷하게 비정규화된 값이 생기면 갱신 지점을
  전부 찾아 동기화할 것.
- **E2E 테스트 타임아웃은 시나리오 길이에 맞춰 키운다**: 핵심 플로우 테스트가
  스텝을 계속 늘려가는 구조라, 실패가 "매번 다른 스텝에서 타임아웃"으로
  나타나면 코드 버그가 아니라 `playwright.config.ts`의 `timeout`이 이제
  안 맞는 것일 가능성이 높다 — 재시도 전에 먼저 이 가능성부터 확인.
- **하단 탭바는 5개 유지**: 화면을 추가할 때 하단 탭에 무조건 넣지 말고, 이미
  홈 화면 버튼/링크로 한 번에 갈 수 있는 기능(기록 작성, 도전 모드 등)은
  탭 대신 홈 화면 링크로 둔다. 탭바에 새 항목을 넣어야 한다면 기존 항목 중
  중복되는 것을 먼저 빼는 걸 검토할 것.
