# 하루별 (Family Growth Diary)

우리 가족만 쓰는 프라이빗 성장 다이어리 PWA. Next.js (App Router) + Supabase.

## 설정

1. Supabase 프로젝트를 만들고 `supabase/migrations/` 안의 SQL을 순서대로 실행합니다
   (Supabase SQL Editor에 붙여넣거나 `supabase db push` 사용).
2. `.env.local.example`을 `.env.local`로 복사하고 프로젝트 URL/anon key를 채웁니다.
3. 개발 서버 실행:
   ```bash
   npm run dev
   ```
4. 가족 중 한 명이 `/signup`에서 **아이디 + 닉네임 + 비밀번호**로 가입 후
   "새 가족 만들기"로 가족을 만들면 6자리 초대 코드가 발급됩니다(가족 피드
   화면 상단에 표시). 나머지 가족은 `/signup` → "초대 코드로 참여하기"로 그
   코드를 입력해 합류합니다. 가입은 열려 있지만, 초대 코드를 모르면 남의
   가족 기록에 접근할 수 없습니다 (RLS로 private-first가 강제됨).

이메일 주소는 전혀 쓰지 않습니다 — 가입 시 내부적으로 무작위 placeholder
이메일을 만들어 Supabase Auth에 등록하고, `login_identities` 테이블이
"아이디 → 그 placeholder 이메일"을 매핑해 로그인 화면에서 아이디+비밀번호로
로그인할 수 있게 해줍니다 (`supabase/migrations/0002_name_based_auth.sql`,
`0004_separate_username_nickname.sql`). 이메일 확인(confirm email) 절차는
DB 트리거로 즉시 처리되므로 Supabase 대시보드의 이메일 인증 설정과 무관하게
항상 동작합니다.

아이디(로그인용, `login_identities.username`)와 닉네임(가족 피드 등에
보이는 이름, `profiles.name`)은 별개입니다 — 설정 탭에서 닉네임을 바꿔도
로그인 아이디는 그대로예요.

## 구조

- `src/app/(app)/` — 로그인 후 화면 (오늘/달력/가족/앨범/설정, 기록 작성·수정, 도전 모드, 개인 공간)
- `src/app/login/`, `src/app/signup/` — 로그인/가입
- `src/app/onboarding/` — 가입 직후 가족 생성/참여 화면
- `src/app/actions.ts` — 서버 액션 (기록 생성/수정, 리액션, 댓글, 가족 생성/참여, 목표, 일정, 로그아웃)
- `src/lib/supabase/` — 브라우저/서버/미들웨어용 Supabase 클라이언트
- `supabase/migrations/` — DB 스키마 + RLS (private-first) + 초대 코드 조회 함수
- `public/manifest.webmanifest`, `public/sw.js` — PWA 매니페스트 + 오프라인 셸 캐싱

## 현재 범위

포함: 로그인, 오늘 기록(카테고리 5종 + 한 줄 + 사진 최대 5장 + 공개범위, 이후 수정
가능 — 사진은 나중에 추가만 가능하고 삭제는 아직 없음), 월간 캘린더(가족 구성원별
작성 표시 포함), 가족 피드 + 리액션 + 댓글, 가족 목표(부모/아이 누구나, 응원 카운트),
캘린더 일정(미용실/약속 등), 사진 앨범(본인 + 가족이 공개한 사진 모아보기).

목표는 결과 달성 압박이 아니라 "사소한 것도 응원받는" 걸 목적으로 해서,
가족간 순위나 벌점은 없고 응원(👏) 카운트만 누적됩니다.

홈 화면에는 "🎁 모은 아이템"도 있습니다 — 기록/목표 활동에 따라 **정해진
규칙으로만** 아이템이 해금돼요 (`src/lib/items.ts`). 랜덤 뽑기는 PRD의
게임화 원칙(도파민 자극용 랜덤 보상 금지)과 맞지 않아서 의도적으로 배제
했습니다.

가족 구성원마다 `/room/[userId]` 개인 공간(미니홈피 느낌)이 있고,
설정에서 나무/별자리/행성/색모음집 중 자기 세계관을 직접 고를 수 있습니다
(가족 전체가 하나로 통일할 필요 없음). 공간에는 모은 아이템과 목표가
표시되는데, 본인이 아닌 경우 그 사람이 가족에게 공개한 것만 보입니다 —
`get_item_stats`가 별도 권한 체크 없이 기존 RLS에 그대로 얹혀 동작하는
구조라, 다른 사람 공간을 봐도 그 사람의 비공개 기록은 절대 새지 않습니다.

"도전 모드"(연속 기록 일수에 따라 동물이 자라는 화면)는 하단 탭에는 없고
홈 화면 "🎁 모은 아이템" 옆 링크로 들어갑니다 — 하단 탭은 5개(오늘/달력/
가족/앨범/설정)로 유지하는 게 원칙입니다 (아래 "설계 원칙" 참고).

보류 (PRD 참고): 원본/디스플레이/썸네일 리사이즈 파이프라인(현재는 원본만 업로드),
Google Calendar 연동, 가족 공유 일정(현재 일정은 개인 캘린더에만 표시), 사진 삭제.

## 설계 원칙 (진행하며 얻은 교훈)

- **비용 추가 금지**: 유료 API·외부 이미지 라이선싱·생성형 이미지 등 운영비가
  드는 요소는 기본적으로 배제. 세계관 비주얼(나무/별자리/행성/색모음집)은
  전부 CSS/SVG로만 그리고, 새 아이템·세계관을 추가할 때도 이 기준을 먼저 통과
  시킬 것.
- **랜덤 없음, 결정론적 해금만**: 어떤 보상이든 "무엇을 줄지"는 고정 ID(아이템
  id, 유저 id 등)를 해시한 값으로 정한다 (`h = (h*31+charCode)>>>0; h % n`
  패턴, `lib/colors.ts`/`lib/creatures.ts`/캘린더 작성자 점 색 등에서 재사용).
  `Math.random()`으로 보상을 결정하지 않는다.
- **RLS로 필터링을 대신한다**: 캘린더·가족 피드·앨범처럼 "내 것 + 가족이 공개한
  것"을 보여줘야 하는 쿼리는 `.eq("user_id", ...)` 필터를 걸지 않고 RLS가
  알아서 좁혀주게 둔다. 단, 새 쿼리를 이렇게 짤 때마다 관련 RLS 정책이 실제로
  존재하는지 먼저 확인할 것 — 존재하지 않으면 조용히 빈 결과만 나온다.
- **Storage RLS는 테이블 RLS와 별개**: `media` 테이블에 family-read 정책이
  있어도 `storage.objects`에 같은 정책이 없으면 실제 파일(서명 URL 발급 포함)은
  가족에게 여전히 안 보인다. 파일이 관련된 기능을 추가할 때는 테이블 RLS와
  스토리지 RLS를 항상 짝으로 점검한다 (마이그레이션 0010 참고).
- **비정규화된 필드는 수동 동기화**: `media.visibility`는 `diary_entries
  .visibility`의 별도 사본이라, 기록 공개범위를 바꿀 때 같이 갱신하지 않으면
  프라이버시 유출로 이어진다. 비슷하게 비정규화된 값이 생기면 갱신 지점을
  전부 찾아 동기화할 것.
- **E2E 테스트 타임아웃은 시나리오 길이에 맞춰 키운다**: 핵심 플로우 테스트가
  스텝을 계속 늘려가는 구조라, 실패가 "매번 다른 스텝에서 타임아웃"으로
  나타나면 코드 버그가 아니라 `playwright.config.ts`의 `timeout`이 이제
  안 맞는 것일 가능성이 높다 — 재시도 전에 먼저 이 가능성부터 확인.
- **하단 탭바는 5개 유지**: 화면을 추가할 때 하단 탭에 무조건 넣지 말고, 이미
  홈 화면 버튼/링크로 한 번에 갈 수 있는 기능(기록 작성, 도전 모드 등)은
  탭 대신 홈 화면 링크로 둔다. 탭바에 새 항목을 넣어야 한다면 기존 항목 중
  중복되는 것을 먼저 빼는 걸 검토할 것.
